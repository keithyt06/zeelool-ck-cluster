架构拓扑

Infrastructure topology

部署在客户已有的 VPC 内。所有节点私网，客户端通过 internal NLB 访问。备份通过 VPC S3 Gateway Endpoint 出私网，不走公网 NAT。

核心数据面：2 CK replica 跨 AZ，3 Keeper 协调，内网 NLB 单入口。AZ 边框橙线 = 可独立故障域。

容错语义（必读）

2-AZ asymmetric fault tolerance

⚠ Primary AZ 挂 = 集群 read-only

默认 keeper_placement 把 2 个 Keeper 放在字典序小的 AZ（默认 az1a）、1 个放在另一个。失去 az1a 时 Keeper quorum 从 3/3 掉到 1/3，写入停摆，读可能降级。失去 az1c 时 quorum 2/3，业务无感。

故障场景Keeper 剩余Quorum集群状态
az1c (Secondary) 挂2 / 3✓ 2/3 ≥ ⌈N/2+1⌉ = 2写入 OK，读 OK
az1a (Primary) 挂1 / 3✗ 破集群 read-only，等 AZ 恢复
单个 Keeper 进程挂（非 AZ 级）2 / 3✓业务无感
单个 CK replica 挂Keepers 不受影响✓NLB 路由到另一 replica，轻微延迟

要"任意 AZ 挂都不停"的对称容错？在 terraform.tfvars 里把 private_subnet_ids 补成 3 个 AZ，并把 keeper_placement 改成 3 AZ 各 1 台。tfvars.example 里有完整示例。

数据流

How data moves

写入路径

ReplicatedMergeTree：写入任一 replica → Keeper 协调 → 另一 replica 异步拉取

备份路径

EventBridge 定时 → 仅 ck-01 执行 → 走 VPC S3 GW endpoint（不经公网）

告警路径

3 个 CW Alarm 覆盖 EB→SSM 失败 + SSM 执行失败两类问题

部署流

From zero to cluster in 4 phases

全程 export AWS_PROFILE=default（或你的 profile）。无需手工创 state bucket —— bootstrap 模块自动做。

0
前置（手工）
VPC + 最少 2 private subnets（跨 2 AZ），每个子网能访问 SSM（NAT 或 SSM endpoint）。
1
Bootstrap state backend
terraform/bootstrap apply 创 S3 state bucket + DynamoDB lock 表，自动生成 backend.hcl。
2
主栈 terraform apply
envs/prod 装载 backend.hcl，apply 创 50+ AWS 资源（EC2 / EBS / NLB / SG / IAM / S3 / SSM Doc / EventBridge / CW Alarm）。
3
Post-apply bootstrap
bootstrap-post-apply.sh 7 步幂等：装 Keeper/CK binary、渲染 config、生成密码存 SSM、smoke。
手工只做 Phase 0（VPC/子网）；Phase 1-3 全自动，全程 ~10 分钟。

客户需要改什么

Files to edit (2 files, ~6 required fields)

1. terraform/bootstrap/terraform.tfvars — 零必填

  • region — 默认 "ap-northeast-1"，改成你的 region
  • profile — 默认空（走 AWS SDK 默认链），可 pin 成 "default"
  • 其余字段（name_prefix / state_bucket_name / lock_table_name）全部有默认

2. terraform/envs/prod/terraform.tfvars — 4 项必填

  • 必填：vpc_id — Phase 0 创的 VPC
  • 必填：private_subnet_ids — map，至少 2 个子网 ID
  • 强烈建议：name_prefix — 客户代号避免 IAM / S3 全局冲突
  • 强烈建议：cluster_name — 不能含 -（CK 限制）
  • 可选：clickhouse_instance_type、clickhouse_data_volume_gb、ssh_key_name、backup_alarm_sns_topic_arn、profile

两个 tfvars 都 gitignored —— 客户 copy 对应的 .example 再改。全部字段注释完整，每个变量在 variables.tf 里有 description。

Instance types

默认值在 terraform/envs/prod/variables.tf。terraform.tfvars.example 里以注释形式列出常见档位，客户要改就取消注释。

角色默认选项（vCPU / RAM）Tokyo 月价适合
Keeper t4g.small t4g.small (2/2 GB) ~$12 默认够 50 张 replicated table
ClickHouse r8g.xlarge r8g.large (2/16 GB) ~$95 MVP / <100M rows/day
r8g.xlarge (4/32 GB) ⭐ ~$208 默认，100–500M rows/day
r8g.2xlarge (8/64 GB) ~$416 重 BI / >500M rows/day

为什么是 r8g 不是 m8g：CK 推荐 8 GB/vCPU（warehousing），m8g 只有 4 GB/vCPU 偏瘦。r8g.large 已经踩 CK "≥ 8 GB RAM" 下限，再低启动会失败。

扩容

Scaling paths

在线 · 无停机

A. 存储扩容

改 clickhouse_data_volume_gb → apply → 用 SSM Doc resize-data-volume 扩文件系统。

⚠ size / iops / throughput 各有 AWS 6h 冷却 —— 要一起改就同一次 apply 提交。

$ terraform apply $ aws ssm send-command --document-name \ $NAME_PREFIX-resize-data-volume --instance-ids <ck-id>
在线 · 无停机

B. 加 replica

在 clickhouse_placement 里加一个 entry，apply 创 EC2 + EBS，bootstrap-post-apply.sh 装软件、渲染配置、挂进集群，Keeper 自动同步。

clickhouse_placement = { "ck-01" = { subnet_key = "az1a" } "ck-02" = { subnet_key = "az1c" } "ck-03" = { subnet_key = "az1a" } # NEW }
Force-new · 需滚动

C. 升机型（vertical）

改 clickhouse_instance_type。会停机换 instance，数据盘靠 prevent_destroy 不丢。建议分两次 -target 滚动，NLB 撑住流量。

$ terraform apply \ -target='module.clickhouse["ck-01"]' # 确认 ck-02 扛住后再: $ terraform apply \ -target='module.clickhouse["ck-02"]'
未自动化

D. 加 shard（horizontal）

当前 1 shard × 2 replica。加 shard 需扩 remote_servers.xml、新 shard 加入 Keeper、旧表 ALTER MOVE PARTITION rebalance。模板 TODO，等有客户 >500M rows/day 规模再做。
